### A. 已确认缺陷（已完成项保留取证）

**A-1 日志错误覆盖判定，并吞掉原始失败类型（2026-10-29 已修复）。**
以下是修复前的复核记录；位置在 runner.py 的日志分析合并段与 log_analysis.py 的行首错误正则。

第一，结构化 checks 全部通过、但日志出现行首 Error 的 case 被判为失败。复核方式：用 command 适配器打印一行无害的 Error 文本并写入全部通过的结果，最终判定为失败，原因字段同时包含“所有必需检查通过”和日志错误文本，而 checks 记录全部为通过。这说明日志文本与结构化结论在最终判定里没有分层。

第二，同一段覆盖逻辑对“未比较”与“分析不完整”两类结果也生效，会被改写成普通失败，原始失败类型只留在原因字符串里，机器无法区分。这比示例中的文案矛盾更值得优先修。

方向：检查结果、日志诊断、解析完整性、最终判定分开保存；日志错误是否改变判定必须由显式策略控制，并支持精确豁免；覆盖前保留原始类型，不再把非“通过”的判定改写成失败。默认策略需与使用方确认，不经审查不默认放宽。

实现：`run.json.analysis` 保留日志合并前的 `result_verdict/result_reason`，`NO_COMPARE` 与 `INCOMPLETE` 不再被日志错误改写为普通失败。默认仍由未豁免的日志 error/fatal 阻止通过；submit 可用 `log_analysis.error_filter` 指定独立 JSON 规则文件，按阶段、可选日志名、错误编号及首行消息精确豁免 error。原始日志与计数不变，命中记录与规则摘要进入运行记录；编译规则进入编译身份。接口和边界见 [Hooks 与日志分析](hooks_and_log_analysis.md#已确认错误的精确豁免)，验证见 [实现状态](implementation_status.md)。

**A-2 LSF 占用残留没有安全恢复路径。**
控制器被杀或取消无法确认终态时，会留下活动占用标记与编译产物读者标记，之后同 case/seed 的运行永久失败，命令行没有任何恢复入口。复核方式：手工写入活动占用标记后以同一 seed 重跑，得到“占用仍活动或未解决”的拒绝。位置在 lsf.py 的占用检查、layout.py 的仿真目录锁、compilation.py 的编译目录预留。

方向：提供只读的状态查询；提供恢复命令，但必须核实作业身份与终态，并在目录锁保护下同时处理活动占用标记与对应的读者标记，留下恢复记录。不得以“超过保留时限”作为删除依据：时间流逝不证明远端作业已经结束，错误删除会让后续运行覆盖仍在写入的日志与编译产物。

**A-3 日志扫描边界的两个缺口。**
其一，位置提取正则只覆盖“文件名后跟冒号行号”和“文件名后跟括号行号”两类，含空格路径会被截断到最后一个空白之后，导致源码位置指向错误文件。其二，扫描超出读取预算时整体标记为不完整，已通过的检查结果会被降级为不完整，机器无法区分“日志太大”与“分析失败”。位置在 log_analysis.py 的位置正则与扫描函数。

方向：补全位置形态并加边界测试；把“预算不足”与“分析失败”拆成不同状态、用不同文案呈现，避免把容量问题当作结果问题。

**A-4 单个执行错误触发输出根隔离，导致后续任务未执行（2026-10-29 已修复）。**
修复前，runner.py 把操作系统错误统一记为基础设施错误并附加 `storage_error`，service.py 随后隔离该输出根。复核时在 local 编译阶段模拟进程创建失败：第一个 case 记录错误，唯一输出根被隔离，后两个 case 仅得到“没有健康输出根”，并未执行。错误码、缺失日志或结果文件只能说明观察到的现象，不能单独证明整块磁盘故障。位置在 runner.py 的错误处理与 service.py 的隔离分支。

方向：按用例记录失败阶段、原始错误码与路径、命令输出，以及日志或结果是否缺失；不根据单次执行错误自动诊断磁盘故障、隔离或切换输出根。后续用例仍按原配置执行，各自记录实际结果。单个 case 的 `run.json` 写失败只使该 case 不能通过；回归 `state.json` 若仍可保存这一错误，其他 case 继续。只有整批状态或 LSF job 占用无法可靠保存时才停止新提交，不伪造完成结论。现有多输出根自动恢复属于既有行为，移除时需同步调整命令行语义、文档与恢复测试。

实现：移除了自动根隔离和切换；一次运行需选择一个输出根。local 单 case 错误及 `run.json` 写入错误不会阻断其他 case，整批状态持久写失败才停止新派发。CLI、恢复语义、文档和故障测试已同步更新；验证记录见 [实现状态](implementation_status.md#2026-10-29-单-case-错误与-lsf-名额修复)。

### B. 需先定契约再实施（已完成项保留取证）

**B-1 重复哈希成本（先定快照语义）。**
每个 attempt 在编译前后各调用一次身份校验，对全部输入重新计算摘要；编译产物校验再算一次。本机实测 2000 个输入文件、合计约 34 MB 时，单个 case 约 0.5 秒，50 个 case 约 4.3 秒。注意元数据相同不保证内容相同，因此元数据缓存不能无条件替代内容校验。

建议顺序：先做单次校验内的去重与调用点合并（报告侧已有按路径与摘要的单次调用内去重，可对齐）；再明确“不可变输入快照”是否作为契约成立（运行期间源码树不变）；最后才引入带失效回退的缓存。若提供跳过证据复验的报告模式，输出必须明确标注“证据未重新验证”，且不能承诺与严格模式判定一致。

**B-2 未知作业与并发额度的关系（2026-10-29 已定策略并实现）。**
修复前，任一作业查询持续未知超过阈值会触发全局取消。该取消同时承担“限制未确认结束作业数”的作用：若未知作业实际仍在运行，单纯释放额度并继续补交会突破并发上限。原讨论方向是允许其他已运行作业继续完成，并让未知作业保留额度；本次已采用“其余名额仍可继续补交”的策略。

实现：未知 job 保留一个并发名额和保护文件；其余真实空闲名额继续补交，所有名额被占满时后续 case 标为未执行。单个 job 错误不设置整批取消信号；未确认终态不发布最终完成记录。

**B-3 调度查询集中化。**
每个活跃作业各有一个查询循环，默认轮询间隔 1 秒；并发 200 时约每秒 200 次查询。方向：按调度配置分组批量查询，只查本控制器记录的受管作业编号，不拉取整个集群；保留单作业查询作为兜底。

**B-4 历史证据、覆盖语义、保留策略与清理必须统一设计。**
当前回归已经使用独立执行根，编译与仿真产物位于批次目录下，记录与报告也在批次目录内，这解决了回归批次之间的互相覆盖。仍然存在的是：同一 case/seed 的单跑会清理并覆盖原目录；回归记录目录只增不减，没有任何清理命令。改动前需要先定义保留哪些证据、证据之间的引用关系、活动作业与写入锁的保护规则、清理的删除前置条件，并同步更新执行阶段文档与其测试。

**B-5 项目迁移与注销。**
bootstrap 要求显式迁移到 schema 2，但没有迁移命令；项目目录被删除或搬移后注册表留下脏条目。发现逻辑明确拒绝新旧配置同时存在，因此迁移必须把旧配置移入备份位置、同步更新注册表、并复用现有事务与中断恢复机制，不能只新增文件。注销与搬移同属一套事务设计。

**B-6 报告体积与自包含契约。**
本机合成 5 万 case 的最终报告约 9.7 MB，分页只作用于页面渲染层，数据整体内嵌。分片会改变“自包含报告”的交付方式，需先明确离线打开、拷贝分享、跨机器查看的要求（分析文件链接已是相对路径，最终报告内为绝对文件地址）。先定交付要求，再决定是否分片。

### C. 可直接实施的小项

**C-1 合并配置缺少删除语义。**
submit 继承的字典合并无法删除父类键，只能覆盖。需定义删除语义并与“hook 阶段整体替换”的既有规则保持一致，补充合并优先级测试。

**C-2 原子写缺少父目录持久化。**
原子写只对文件做落盘，未对父目录落盘，掉电后目录项可能不一致。补齐时需注明平台边界。

**C-3 编译输入依赖分类细化。**
计划已区分全量输入与编译相关输入，后续是细化分类：确保命令构建所需的 Makefile、脚本、include 目录既不被漏掉，也不把无关测试资源算进编译身份。

**C-4 归属标记补模式与提交名。**
运行记录已包含 mode，但目录归属标记的身份字段未包含 mode 与提交名。补字段属于归属校验契约变更，需同步兼容策略与旧标记迁移。

**C-5 LSF 工具缺失提示。**
规划阶段已报告“可执行文件不可用”，可改善文案（说明切换本地调度或安装客户端）。默认使用 LSF 是当前明确约定，自动切换属于行为变更，需单独评审。

**C-6 默认检查集的取舍。**
默认 RTL 模板显式配置为只要求功能检查，可以正常加载。若后续要让 golden 成为默认检查，需同时调整模板、加载缺省值与文档，并加“默认模板可直接通过配置检查”的回归测试。

### D. 发布与安装

拆成独立任务，不与执行核心混在一起：

- 安装器在符号链接调用下的安装根判定一致性，以及共享安装的读取验证。
- 安装失败回滚的具体触发条件需要写清楚（有效安装凭据会使安装提前返回），并分析“删除时是否存在同版本运行中进程”的保护。
- 仓库没有持续集成，测试只在本地执行；未提交改动较多时需要先建立可重复的全量回归基线。
- 包元数据缺少许可证、分类器与项目链接。
- 离线包与校验和流程需要在真实 Release 上验收；跨目标平台的依赖下载需要在目标机验收。

### 实施顺序

1. 取证与复现：为每条附复现命令、源码位置与提交身份，并跑一次全量回归建立基线。
2. 定契约：A-1 的日志判定规则、B-4 的证据保留与覆盖语义。这两项决定后续实现形态。
3. 实现：A-2 的安全占用恢复、B-3 的分组查询、B-1 经去重与快照边界验证的哈希优化。
4. 统一设计：B-4 历史证据与清理、B-5 项目迁移注销，一次完成契约、实现与文档。
5. 按实测收益：B-6 报告体积、C 组小项、D 组发布安装。

本地 fake 与进程级调度桩通过不代表真实 EDA 或 farm 验收。
